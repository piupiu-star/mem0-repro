## 1. Project summary and what I set out to reproduce

**The system.** [Mem0](https://github.com/mem0ai/mem0) is a long-term memory
layer for LLM agents: conversation turns are ingested into a memory store,
relevant memories are retrieved per question, and an answerer conditions on them.
It is agentic in the sense that matters here — ingestion is itself a multi-step
LLM pipeline (extract candidate facts → compare with existing memories →
ADD/UPDATE/DELETE), so "what the system knows" is decided by the system, not by
the caller.

**The claim.** Mem0's README reports **92.5 % LoCoMo accuracy** on its managed
platform, with a headline of **>90 % fewer tokens** and **91 % lower p95
latency** than a full-context baseline (arXiv:2504.19413). LoCoMo (Maharana et
al., arXiv:2402.17753) is a long-conversation QA benchmark: 10 conversations of
19–32 sessions each, questions split into multi-hop, temporal, open-domain,
single-hop and adversarial.

**What I reproduced.** One benchmark, one conversation, all four scored
categories:

| | |
|---|---|
| benchmark | LOCOMO-10, `snap-research/locomo`, conversation 0 (19 sessions, reference date 22 Oct 2023) |
| questions | first 120 in-scope questions: multi-hop 32, temporal 37, open-domain 13, single-hop 38 (adversarial excluded, as the authors do) |
| metric | LLM-as-a-Judge accuracy: the authors' verbatim judge prompt and parsing, but run on `deepseek-chat` rather than their default `gpt-5` (§2) |
| reference numbers | README 92.5 % overall + per-category; paper's relative token and latency claims |

**What I modified.** One ablation: disabling Mem0's LLM fact-extraction stage
(`add(..., infer=False)`), so raw turns are stored verbatim instead of being
rewritten into facts. It is isolated (one flag), measurable (paired test on
identical questions), and it directly targets the mechanism the paper credits for
its accuracy.

**Headline result.** **65.3 %** overall (± 0.5 over three trials) against 92.5 %
reported. Two of four categories beat the reported score, one is within 7 points,
one collapses. The collapse is traced to a single, reproducible cause in the
open-source SDK, and excluding that one category the rest of the benchmark matches:

> Excluding the temporal block, the remaining 83 questions score
> **229/249 = 92.0 %** across three trials, against 92.5 % reported. That is a
> measurement, not arithmetic: the 27.2-point headline gap is one category, one
> missing parameter, one SDK decision.

## 2. Setup notes

**Environment.** Windows 11 (25H2), Python 3.11.6, `mem0ai==2.2.1`,
`qdrant-client==1.20.0`, `fastembed==0.9.1`, `spacy` + `en_core_web_sm`. No
Docker, no Node, no GPU; `results/pip-freeze.txt` records the full freeze.

**Data.** `locomo10.json` downloaded at run time (~10 MB, gitignored). Prompts
and answer post-processing are copied verbatim from `mem0ai/memory-benchmarks`
(`benchmarks/locomo/prompts.py`, Apache-2.0) and attributed in `src/prompts.py`.
The released file also carries `session_N_date_time` keys up to N = 35 with no
matching turn array. `src/locomo.py` matches only real turn arrays, so the
reference date handed to the answer prompt is the true last session
(22 Oct 2023), not the orphan key (4 Jan 2024).

**Keys.** `DEEPSEEK_API_KEY` lives in `.env`, which is gitignored; only
`.env.example` is tracked. No key appears in any commit or in any result file.

**Compute and budget.** Everything runs on one consumer laptop. Every LLM call the
harness issues records its own token usage, and at DeepSeek's published prices
($0.27 / M input, $1.10 / M output) the study bills about **$3.80** in total:
$1.97 for the three headline configurations, $1.74 for trials 2–3, and $0.09 for
one run I discarded as invalid. That number is a **lower bound**, not a total:
Mem0's internal extraction calls are issued inside `add()` and never pass through
the tracker, so extraction-on ingestion costs more than it records. Ingestion of
the 419-turn conversation takes 535 s with extraction on and 10 s with it off.

**Model substitution (declared, per the brief's Edge case A).**
`deepseek-chat`, provider `deepseek`, base URL `https://api.deepseek.com`,
temperature `0.0` for extraction / answering / judging, `max_tokens` 600 (answer)
and 120 (judge), `top_p` unset and identical in every configuration. The embedder
is `fastembed:BAAI/bge-small-en-v1.5` because DeepSeek exposes no embedding
endpoint — a **forced** second departure, not a choice (see §6, row 5). No prompt
text was modified.

> **Results are not directly comparable to the paper because the underlying LLM
> differs.**

They also differ because the embedder differs, because the **judge** is a
different model, and because the code I ran is a later algorithm than the paper
describes (§6, row 11). Those are four confounders, and they are listed rather
than hidden.

The judge deserves its own paragraph. The authors'
`benchmarks/locomo/run.py` defaults **both** `--answerer-model` and
`--judge-model` to `gpt-5`. Here both are `deepseek-chat`. Swapping the answerer
changes what is being measured; swapping the judge changes the *measuring
instrument*. The verbatim judge prompt fixes the rubric but not the grader, so
every accuracy number in §4 is gpt-5's reading against another model's reading,
not two readings of one instrument. Nothing I could run tonight removes this — it
is the first thing I would fix with access to one more model.

What *is* held fixed is everything that defines the task and the rubric: the
dataset, the question set, the retrieval depth, the judge prompt text, the answer
post-processing and the arithmetic of the token counts.

## 3. Reproduction targets and metric definitions

**R1 — absolute accuracy (primary).** LoCoMo accuracy = fraction of questions the
judge labels `CORRECT`, using the authors' judge prompt, with their rule that
category-3 gold answers are truncated at the first `;`. Reported target: 92.5 %
overall, with per-category 91.2 / 91.3 / 72.7 / 92.0.

The 92.5 % comes from the README of the **v3** codebase and is measured on Mem0's
**managed platform**. The authors state that platform scores include proprietary
optimisations "not available in the open-source SDK" and that open-source users
should "expect directionally similar gains but not identical numbers". So R1 is
not a like-for-like target: it is the number a reader would compare against, and
the interesting question is how far off it is and whether the direction survives.

**What "same evaluation script" means here.** I did not run the authors'
`benchmarks/locomo/run.py`. I wrote `src/run.py`, which reproduces its loop
(ingest → search → answer → judge, per cutoff). The evaluation *logic* is held
fixed wherever it is observable: the judge system prompt and judge template are
byte-identical copies, `preprocess_answer` is copied, and the answer prompt's
memory-rendering glue was diffed against the authors' `get_answer_prompt` — which
is how one real mismatch was found and fixed (§6, row 9). What is **not** held
fixed is the script's identity: this is a re-implementation, and the diff is the
only evidence that it matches. The brief's phrase "same evaluation script" is
therefore satisfied in substance, not literally, and I would rather say so than
claim a fidelity I did not test by running their file.

**R2 — relative efficiency (secondary).** Two claims that need no judge and
therefore cross fewer unknowns: **>90 % token saving** and **91 % lower p95
latency**, both versus full-context. Tokens per query = the answer prompt's
prompt tokens; the full-context baseline stuffs the entire 419-turn transcript
into every prompt, which is what the paper's baseline does.

**R3 — version drift (a finding, not a target).** The paper describes the v2
algorithm; repository `main` is the v3 "New Memory Algorithm". Any absolute
comparison across those two code lines is measuring a different system.

**Cost/latency instrumentation.** Retrieval latency is timed around
`memory.search()` only, separately from end-to-end latency (retrieval + answer +
judge), because the 0.88 s p50 and 91 % p95 figures are *search* claims. Mixing
them would manufacture agreement.

## 4. Results: my numbers against the reported numbers

All figures below are at the authors' retrieval depth (top-200), pooled over three
trials, and come from `results/summary.md`. Table 1 there also reports the top-10
curve and the spread across trials.

### 4.1 Accuracy (R1)

| category | reported | measured | verdict |
|---|---|---|---|
| overall | 92.5 | **65.3 ± 0.5** | 27.2 points below |
| single-hop | 91.2 | **96.5** | 5.3 above |
| multi-hop | 91.3 | **84.4** | 6.9 below |
| open-domain | 72.7 | **97.4** | 24.7 above |
| temporal | 92.0 | **5.4** | 86.6 below |

Two categories beat the reported score, one is within 7 points, and one is
destroyed. A single averaged number hides all of that, which is why I did not
report one. Per-trial stability is ± 0.5 points overall, so the collapse is not
a sampling accident.

### 4.2 The temporal collapse, and its cause

Temporal accuracy is 6 correct out of 111 question-instances — 2 out of 37 in
every trial, with no variation at all. This is not noise and not an
answering-model limitation — the model answers confidently and wrongly, because
the memories it retrieves are wrong. One example, verbatim from
`results/evidence/repro_mem0_ext_temporal_wrong.md`:

- **Question.** When did Caroline go to the LGBTQ support group?
- **Gold.** 7 May 2023
- **Retrieved memory.** "Caroline attended an LGBTQ support group on November 11,
  2026, and found the experience very powerful"
- **Generated.** November 11, 2026 → **WRONG** (judge: "not within 14 days of the
  gold date of 7 May 2023")

The stored memory carries a date three years in the future, for a conversation
that took place in 2023. Root cause, traced through the SDK source:

1. The authors' LOCOMO runner anchors each session with
   `mem0.add(messages, user_id, timestamp=session_epoch)`
   (`benchmarks/locomo/run.py`, ingest loop). This is what allows relative
   expressions — "a few weeks before that", "last Tuesday" — to be resolved
   against the conversation's own clock.
2. In `mem0ai==2.2.1`, the open-source `Memory.add()` **refuses** that parameter:
   `timestamp` is gated in `mem0/memory/notices.py` and raises
   `ValueError: The timestamp parameter is not supported by the OSS Memory SDK.`
   `reference_date` is gated identically.
3. My adapter catches the refusal and retries without `timestamp`, so ingestion
   succeeds — but extraction now resolves every relative date against the **wall
   clock of the machine**, which at run time was November 2026.
4. Extraction then *writes the wrong date into the memory text itself*. The error
   is not recoverable at answering time: the prompt already forbids outputting
   2025/2026, and the model obediently copies the date the store gave it.

That is the whole story of the headline gap. The paper's temporal result depends
on a code path that the open-source distribution does not permit, and the failure
is silent: ingestion reports success, the store fills up, and only the temporal
questions reveal it.

### 4.3 Making the headline gap interpretable

On the 83 questions the timestamp gate does not touch, I measure **229/249 =
92.0 %** across three trials, against 92.5 % reported. The 27.2-point headline
gap is therefore not evidence of a broadly weaker system: it is one category,
one missing parameter, one SDK decision.

The multi-hop shortfall (84.4 vs 91.3) is **not** explained by this. I have no
evidence for its cause and therefore do not attribute one.

### 4.4 Efficiency (R2)

| claim | reported | measured (mem0, extraction on) | measured (full-context) |
|---|---|---|---|
| prompt tokens / query | 7.0 K | 10.1 K | 24.4 K |
| token saving vs full-context | >90 % | **58.9 %** | — |
| retrieval p50 | 0.88 s | **0.063 s** | no retrieval step |
| retrieval p95 | — | 0.141 s | no retrieval step |
| end-to-end p50 | — | 3.55 s | 3.80 s |
| end-to-end p95 | — | 5.12 s | 4.78 s |

*Latency is quoted from trial 1 on both sides: the full-context baseline ran one
trial while mem0 ran three, and comparing pooled mem0 latency against a single
full-context trial would measure when each run happened, not the systems.*

**Tokens: the direction reproduces, the magnitude does not.** 58.9 %, not >90 %;
mem0 still uses 2.4× fewer prompt tokens than full-context.

**The 0.88 s p50 is not a like-for-like win.** My retrieval is 14× faster, but it
runs against a local Qdrant file store on a laptop, not the managed platform.

**The 91 % p95 reduction is not measurable as stated.** It is a reduction
*relative to full-context*, which performs no retrieval, so the ratio is
zero-over-zero. Framed end-to-end, mem0 is **7.2 % slower at p95** while being
faster at p50 (3.55 s vs 3.80 s). Both configurations issue the same two calls,
so this is tail behaviour, not call count: mem0's answer prompts vary with what
was retrieved and the long ones cost more. A memory layer can be cheaper on
average and still lose in the tail. The claim is not false — it is a
*search-latency* claim — but reporting it as an end-to-end one inflates it.

### 4.5 Accuracy against full-context

Full-context scores **99.2 %** (119/120, one trial — a single wrong answer in the
whole set, so there is no spread left to measure), against mem0's 65.3 %. In my
setup memory is strictly dominated: fewer tokens, much lower accuracy. The honest
reading is that Mem0's value proposition here is cost, not accuracy, and that the
cost advantage is 58.9 % rather than the advertised >90 %.

### 4.6 Version drift (R3)

The paper describes the v2 algorithm; the repository I ran is v3. The README's
92.5 % is a **managed-platform v3** number. So my comparison crosses two gaps at
once — v2→v3, and platform→open source — and neither is separately observable
from here. This is why I treat 92.5 % as a reader's reference point rather than a
target to hit, and why the per-category pattern (two above, one near, one
destroyed) is more informative than the aggregate.

## 5. My modification and its measured effect

**The change.** `add(..., infer=False)` — disable Mem0's LLM fact-extraction
stage, so each turn is stored verbatim instead of being rewritten into facts.

**Why this one.** The paper's accuracy story rests on extraction: the memory
layer decides *what is worth remembering* and rewrites it into compact facts. If
that stage is also where the temporal damage happens (it is — §4.2), then turning
it off is the smallest change that tests the mechanism rather than decorating it.
It is one boolean, applied identically to every ingest call, carried into every
fallback path so a signature change cannot silently re-enable extraction.

**Result (top-200, three trials pooled, 360 question-instances).** Counts are
shown as well as percentages, because at these sample sizes one question is worth
2.6 points in open-domain and 0.9 in multi-hop:

| category | n | extraction ON | extraction OFF | change |
|---|---|---|---|---|
| overall | 360 | 235 = 65.3 % | 279 = 77.5 % | **+12.2** |
| temporal | 111 | 6 = 5.4 % | 41 = 36.9 % | **+31.5** |
| multi-hop | 96 | 81 = 84.4 % | 89 = 92.7 % | +8.3 |
| single-hop | 114 | 110 = 96.5 % | 112 = 98.2 % | +1.7 |
| open-domain | 39 | 38 = 97.4 % | 37 = 94.9 % | **−2.5** |

The overall gain is **44 questions out of 360**. Thirty-five of them are temporal,
eight multi-hop, two single-hop — and open-domain moves by exactly **one**
question in the wrong direction. At n = 39 that is noise, so I do not interpret
it, and I do not present the modification as uniformly beneficial: it is a large
gain in one category and a wash elsewhere.

**Paired test.** Both configurations answer the identical 120 questions, so the
comparison is paired. Exact McNemar on the discordant pairs, and a paired
bootstrap for the interval:

| cutoff | baseline | modified | flips | delta | 95 % CI | McNemar p |
|---|---|---|---|---|---|---|
| top-200 (3 trials) | 235/360 | 279/360 | 51 gained / 7 lost | +12.2 pp | [+8.3, +16.4] | **< 0.001** |
| top-10 (1 trial) | 74/120 | 76/120 | 8 gained / 6 lost | +1.7 pp | [−4.2, +7.5] | 0.791 |

The top-200 figure pools three trials, so `n = 360` is three repeats of the same
120 questions rather than 360 independent observations — pooling inflates `n` and
makes the p-value optimistic. The per-trial test is the conservative reading, and
it agrees: +12.5, +12.5 and +11.7 pp, i.e. **+12.2 ± 0.5**, with the direction
never reversing. The effect is stable, not a lucky trial.

**The judge swap does not weaken this comparison.** Both arms answer the same
questions and are graded by the same DeepSeek judge, so the A/B delta is two
readings of one instrument. The judge confounder in §2 affects the distance from
the paper's 92.5 %, not the distance between my two configurations.

At the paper's operating depth the effect is established; at top-10 it is not.
That contrast is itself informative: the gain only appears when the answerer is
allowed to see a broad slice of memory, which fits the date-in-the-text
explanation — a wrong date has to be *retrieved* before it can mislead.

**Why it helps, and how much of it I can attribute.** Two channels change when
extraction is disabled, and I cannot fully separate them:

1. **Date anchoring.** With extraction on, relative expressions are resolved
   against the wall clock and written into the memory text (→ "November 11,
   2026"). With extraction off, the original wording survives, so the answerer
   sees the conversation's own phrasing and its session dates.
2. **Granularity.** 503 extracted facts become 419 raw turns. Raw turns preserve
   connective detail that extraction drops — the "before that", "the same person"
   phrases that multi-hop questions chain through — which is a plausible partial
   explanation for the eight extra multi-hop questions.

The per-category pattern points at channel 1: temporal moves +31.5 while
single-hop moves only +1.7. But I report this as a hypothesis supported by
the pattern, not as an isolated causal estimate — a clean separation would need a
third arm that re-enables extraction *and* fixes the clock, which the OSS SDK does
not allow me to construct.

**Cost of the change.** `infer=False` is not free:

| | extraction ON | extraction OFF |
|---|---|---|
| ingest wall clock | 535 s | **10 s** |
| memories stored | 503 | 419 |
| prompt tokens / query | 10.1 K | 11.4 K |
| token saving vs full-context | 58.9 % | **53.3 %** |
| extraction LLM calls during ingest | yes — inside `add()`, untracked | **0** |

So the modification trades about 1.3 K tokens per query for 12.2 accuracy points
and a 53× faster ingest that makes no extraction calls at all. For a system whose
selling point is cost, that is a real trade-off rather than a free win — and it
pushes the token-saving claim further from the advertised >90 %, not closer.

**Limitation.** At top-200 the raw configuration retrieves 200 of its 419 stored
turns — nearly half the conversation — so the retriever is doing relatively
little discrimination at that depth. Part of the gain could be a
"more-context" effect rather than a "better-memory" effect. The top-10 column
(where the gain disappears) is consistent with that reading, and I flag it rather
than picking the favourable depth.

## 6. Debug diary

Each row is something that broke on this machine, what it actually was, and what
fixed it. Rows 6, 9 and 10 are the ones that changed my conclusions rather than
just my code.

| # | Symptom | Root cause | Resolution |
|---|---|---|---|
| 1 | `RuntimeError: Storage folder ~/.mem0/migrations_qdrant is already accessed by another instance of Qdrant client` | mem0 v3 opens a **global** telemetry Qdrant store, so a process may hold only **one** `Memory` instance | one configuration per process; enforced in `src/run.py` |
| 2 | `ValueError: Top-level entity parameters frozenset({'user_id'}) are not supported` | mem0ai 2.x changed the search convention, and it raises `ValueError`, not `TypeError` — a `except TypeError` fallback never fires | call `search(query, filters={"user_id": ...}, top_k=...)`, keep old forms as fallbacks |
| 3 | `Failed to load spaCy lemma model` | the plain `mem0ai` wheel silently degrades v3's multi-signal retrieval to dense-only | install `mem0ai[nlp]` + `en_core_web_sm`; now a documented requirement |
| 4 | official OSS evaluation path is `docker compose`-only | the authors' harness wraps Mem0 in a FastAPI service | drive the SDK directly; deviations recorded in `README.md` §4 |
| 5 | DeepSeek exposes no `/embeddings` endpoint | model substitution cannot be a single variable | local `fastembed`; recorded as a **forced** confounder |
| 6 | temporal accuracy 2/20 while multi-hop scored 14/15 | `timestamp=` is refused by the OSS SDK (gated in `mem0/memory/notices.py`), so extraction anchored dates to the wall clock and wrote 2026 dates into memories | proven against the authors' runner, which *does* pass `timestamp=session_epoch`; reported as the main finding rather than patched away |
| 7 | ingest log printed `stored=20` for a 419-turn conversation | `Memory.get_all()` defaults to **`top_k=20`**, so any bare call truncates and reports a fabricated total; the store behind that log held several hundred memories (503 in the run that produced the reported numbers — §5) | pass `top_k=100_000`; cross-checked with `QdrantClient.count(exact=True)` |
| 8 | run exited 1 although every artefact was written | PostHog/Qdrant shutdown noise on stderr, which PowerShell promotes to a terminating error | redirect to a log and judge success by artefact count, not exit code |
| 9 | every memory was prefixed `(2026-11-12)` where the authors render `(Thursday, November 12, 2026)` | my date formatter had a shortened `strptime` tuple; mem0's ISO timestamps only match the authors' `%Y-%m-%dT%H:%M:%S.%f%z` candidate after `[:26]` truncation and `%z` removal | copied `_to_human_date` verbatim, verified identical output on 8 input shapes, archived every answer produced under the old prefix to `results/_archive_v1_datefmt/` and re-ran |
| 10 | 120 questions scored against **zero** memories without raising | my own "never abort, score it 0" guard turned a hard failure into a plausible table | added a preflight that refuses to evaluate a store reporting 0 memories |
| 11 | paper (v2) vs repository (v3) algorithms differ | the repo iterated after publication; the README score is a managed-platform v3 number | declared as R3; absolute numbers treated as a reference point, not a target |

**The pattern worth stating.** Four of the eleven were *silent*: ingestion
"worked", the store "had 20 memories", the evaluator "scored 120 questions", the
date "was rendered". Each produced a number that looked like a finding. The only
thing that caught them was dumping per-question evidence and reading it — gold
answer next to generated answer next to the memories that were retrieved. An
aggregate score alone would have let me report "Mem0 reproduces poorly", which
would have been a false statement about the authors' system rather than a true
statement about my pipeline.

## 7. Conclusions

### What reproduces

- **The per-category picture, in part.** Single-hop reaches **96.5 %** against a
  reported 91.2 %, and open-domain **97.4 %** against 72.7 %. Multi-hop lands
  within 7 points (84.4 vs 91.3). The system is not uniformly weaker than
  claimed: it is strong on exactly the question types that do not depend on dates.
- **The direction of the efficiency claim.** Mem0 uses **2.4× fewer prompt tokens
  than full-context** (10.1 K vs 24.4 K per query). That is the substance of
  "memory beats stuffing the transcript", and it survives.
- **The pipeline itself.** Extraction, multi-signal retrieval, collection
  maintenance and answering all run end-to-end on a consumer laptop with no
  Docker, on a 419-turn conversation, for about a dollar.

### What does not reproduce

| claim | reported | measured | why |
|---|---|---|---|
| overall LoCoMo accuracy | 92.5 % | 65.3 % | dominated by the temporal collapse below |
| temporal accuracy | 92.0 % | 5.4 % | the OSS SDK refuses the `timestamp` anchor the authors' runner passes |
| non-temporal subset | 92.5 % | 92.0 % (229/249) | the 83 questions the gate does not touch |
| tokens per query | 7.0 K | 10.1 K | different embedder, different chunking, different platform |
| retrieval p50 latency | 0.88 s | 0.063 s | platform measurement vs local Qdrant file; **not** a like-for-like win |
| token saving vs full-context | >90 % | 58.9 % | direction holds, magnitude does not |
| p95 latency reduction | 91 % | not measurable as stated; −7.2 % end-to-end | full-context has no retrieval step, so the ratio is 0/0 |

### Why

Three causes, in order of how much they explain:

1. **A feature gate, not a bug.** Temporal accuracy does not degrade — it is
   destroyed, because the anchor that makes dates resolvable is unavailable in
   the open-source package. The authors' runner passes `timestamp=session_epoch`;
   `mem0ai==2.2.1` raises `ValueError: The timestamp parameter is not supported by
   the OSS Memory SDK.` Everything downstream inherits wrong dates, and the
   failure is silent at ingest. This is worth more than a matching percentage
   would have been: it tells a practitioner exactly which capability they lose by
   self-hosting.
2. **Platform vs open source, across algorithm versions.** The 92.5 % is a
   managed-platform v3 number; the paper describes v2; I ran open-source v3. Three
   systems, one comparison, as the authors' own README says.
3. **Forced substitution.** DeepSeek has no embedding endpoint, so the embedder
   changed too. Token counts and latency therefore cross more than one variable,
   which is why I lean on the per-category pattern and the paired test rather than
   on absolute agreement.

### What would change the conclusion

If the same harness is pointed at the **managed platform** with the authors'
original models, the temporal block should recover and the headline should move
towards 92.5 %. If it does not, the platform-vs-OSS explanation is wrong and
something else is doing the work. That is the single most informative follow-up,
and it costs a platform subscription rather than more code.

### Recommendations to future users

1. **If your task involves dates, do not self-host Mem0 unpatched.** Expected
   temporal accuracy is near zero, and nothing warns you.
2. **Never trust `Memory.get_all()` for a count.** It defaults to `top_k=20` and
   will report 20 memories for a store of 500; use `QdrantClient.count(exact=True)`.
3. **Dump per-question evidence, not just aggregate scores.** Four of the eleven
   problems in §6 were silent failures that produced plausible numbers.
4. **Check whether a latency claim is a search claim.** A 91 % reduction in
   *retrieval* latency is compatible with being slower *end-to-end*; comparing the
   wrong pair manufactured a 98-point disagreement in my own table.
5. **Measure full-context before adopting memory.** It scored 99.2 % here at 2.4×
   the tokens, so the trade depends on your budget and accuracy floor, not on the
   memory layer's reputation.
6. **`infer=False` is a cheap, high-value ablation.** One flag, no API calls, 53×
   faster ingest, and here it *improved* accuracy by 12.2 points (p < 0.001).

## Appendix: reproducing this report

```powershell

```

Total: about 45 minutes of wall clock and roughly $4 of API billing for the
answer+judge stage, plus Mem0's untracked extraction calls during ingest (§2).
